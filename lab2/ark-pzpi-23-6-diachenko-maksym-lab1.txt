2 ОПИС ВИКОНАНОЇ РОБОТИ

2.1 Опис інженерних рішень та архітектури системи

Для серверної частини програмної системи «EcoResource Analytics» обрано підхід REST API,
оскільки він забезпечує стандартизовану взаємодію клієнта і сервера через HTTP-методи та
обмін даними у форматі JSON. Таке рішення спрощує інтеграцію веб-клієнта, мобільного
клієнта та/або сторонніх сервісів.

Технічний стек реалізації:
- Платформа: Node.js.
- Веб-фреймворк: Express (маршрутизація, middleware, обробка запитів).
- База даних: PostgreSQL (реляційна модель, зв’язки, цілісність, транзакції).
- ORM: Sequelize (опис моделей, міграції, CRUD-операції, робота з запитами).
- Контейнеризація: Docker + docker-compose для підняття PostgreSQL локально.
- Перевірка API: curl (PowerShell), браузер (ендпоінт /health).

Архітектурно сервер складається з:
- шару маршрутизації (ендпоінти /api/*),
- шару контролерів/сервісів (логіка обробки запитів),
- шару доступу до даних (Sequelize models),
- бази даних PostgreSQL.

Для авторизації використано JWT-токен (Bearer Token) у заголовку Authorization, що дозволяє
контролювати доступ до API та відокремлювати публічні маршрути (наприклад /health, /api/auth/login)
від захищених (наприклад /api/regions, /api/indicators, /api/measurements).


2.2 Проєктування БД та ER-модель

У БД виділено основні сутності предметної області «аналіз природних ресурсів»:
- Region (регіон вимірювань),
- ResourceType (тип ресурсу: вода/земля тощо),
- Unit (одиниця вимірювання),
- Indicator (показник ресурсу),
- DataSource (джерело даних),
- Measurement (вимірювання показника у регіоні за дату),
- User, Role (користувачі та ролі доступу для роботи з API).

Основні зв’язки:
- Indicator належить до ResourceType та Unit (багато-до-одного).
- Measurement посилається на Indicator, Region, DataSource та (опційно) на User (created_by).
- User належить до Role (багато-до-одного).

У звіті наведено:
- UML діаграму прецедентів серверної частини (Рисунок 2.1),
- ER-діаграму (Рисунок 2.2),
- діаграму структури БД / схему таблиць із ключами (Рисунок 2.3).


2.3 Нормалізація даних (1NF–3NF)

1NF:
- Усі таблиці мають атомарні значення полів.
- Відсутні повторювані групи атрибутів в одному полі.

2NF:
- У таблицях з первинним ключем (id) усі неключові атрибути залежать від усього ключа.
- Для Measurement ключовим ідентифікатором виступає id, а індикатор/регіон/дата винесені
  в окремі поля з зовнішніми ключами.

3NF:
- Усунені транзитивні залежності: довідники (Region, Unit, ResourceType, DataSource, Role)
  винесені в окремі таблиці, а в Measurement та Indicator використовуються лише посилання (FK).


2.4 Реалізація доступу до БД (ORM) та CRUD

Доступ до БД реалізовано через Sequelize. Створено:
- міграції (migrations) для створення таблиць та обмежень (PK, FK),
- сіди (seeders) для початкових даних (ролі, адміністратор, тестові регіони, індикатори тощо),
- моделі (models) для основних сутностей.

CRUD-операції реалізовано для ключових сутностей:
- перегляд довідників (regions, indicators),
- створення/перегляд вимірювань (measurements),
- авторизація користувача та отримання JWT (auth/login).

Примітка щодо seed:
Сіди ініціалізують початкові довідникові записи з фіксованими id. Тому повторний запуск seed
на вже заповненій БД може викликати помилку:
“Validation error: Key (id)=(1) already exists.”
У процесі демонстрації достатньо:
- або виконувати seed лише один раз;
- або, якщо потрібно “почати з нуля”, виконати повне очищення volume:
  docker compose down -v
  docker compose up -d
  npm run db:migrate
  npm run db:seed


2.5 Специфікація API (REST)

Основні ендпоінти:

1) Перевірка працездатності сервера
- GET /health
Відповідь:
{ "ok": true }

2) Авторизація (отримання JWT)
- POST /api/auth/login
Тіло запиту (JSON):
{ "email": "admin@nure.ua", "password": "admin123" }
Відповідь:
{ "token": "<JWT>" }

3) Довідники
- GET /api/regions (потрібен Authorization: Bearer <token>)
Відповідь: список регіонів.

- GET /api/indicators (потрібен Authorization: Bearer <token>)
Відповідь: список індикаторів.

4) Вимірювання (CRUD частково)
- POST /api/measurements (Authorization + JSON)
Тіло запиту:
{
  "indicator_id": 1,
  "region_id": 1,
  "measured_on": "2026-01-01",
  "value": 12.34,
  "data_source_id": 1
}
Відповідь: створений запис Measurement.

- GET /api/measurements?regionId=...&indicatorId=...&dateFrom=...&dateTo=...
(Authorization)
Відповідь: список вимірювань за фільтрами.


2.6 Перевірка (тестування) взаємодії API з БД

Для запуску PostgreSQL використано docker-compose:
- docker compose up -d

Після запуску БД виконано міграції та (за потреби) сіди:
- npm run db:migrate
- npm run db:seed  (виконується один раз або після docker compose down -v)

Для перевірки API виконано:
- перевірку сервера: GET /health у браузері,
- логін і отримання JWT-токена,
- запити до /api/regions та /api/indicators з Authorization,
- створення вимірювання через POST /api/measurements,
- читання вимірювань через GET /api/measurements із параметрами фільтрації.

Таким чином підтверджено коректність взаємодії серверної частини з PostgreSQL через ORM та
правильну обробку API-запитів клієнта.
